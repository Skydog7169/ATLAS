## The moves

### Build the 'what changed' engine: deltas plus a seen-set, shared by every surface
Why: This is the returning visitor's main job. Only 14 of last week's 49 entries were real signals, and they look identical to the 35 re-assessments. 'Since last visit' silently loses items merged after Mark read. The ticker picks items alphabetically (Albania first, the biggest wars dropped). The watchlist feeds nothing, and the strip's count doesn't match the panel it opens.

What: history.ts attaches prev and delta (new/up/down/same) to each ChangeItem, mirrored in build-feeds.mjs and send-digest.mjs. Replace date comparison with a seen-set in atlas.lastVisit.v2, keyed `${kind}:${id}:${date}`, with v1 migration. Rank tickerItems by delta, then intensity, then date. FeedList shows worded tags ('▲ Escalated · low → medium', '▼ Eased', 'New') and collapses 'N re-assessments, no change'. ChangesView defaults to 7 days, grouped New / Escalated / Eased / Re-assessed. The strip leads with followed items and opens the panel on the same since-window, with Mark read available there too. Watchlist rows show date, intensity, delta and an unread dot. Unrest gets its own palette and 'Unrest · High' tags. Add the missing Unrest section to the digest.

### Quick win: Fix the changes-feed row layout
Give .inline-link display:inline and text-align:left. Put the kind tag on its own nowrap row as a pill, and clamp the detail text to 3 lines with CSS instead of JS slicing.

### Quick win: Ticker: pause control, kind-aware tags, an honest filter name
Add a 'Pause feed' button (aria-pressed, persisted) that applies the reduced-motion scroller styles. Tags read 'Conflict · High' or 'Unrest · High', with the unrest palette and triangle. Rename the ticker filter to 'Starred only' with a funnel icon, and label the strip 'FEED · STARRED' when it's on.

### Quick win: Digest and RSS reach readers
Add the missing Unrest section to send-digest.mjs (28 of 50 items are currently dropped). Add RSS and JSON Feed autodiscovery links to index.html, plus an 'RSS' text button in the Changes and Watchlist panels.

### Quick win: Watchlist survives two tabs and blocked storage
Listen for storage events and merge on toggle instead of overwriting. When a write fails, show 'THIS TAB ONLY'. Render unresolved ids as 'No longer tracked' rows with only a Remove action, so they no longer leave a phantom open panel.

## How to work
1. `git fetch origin main && git checkout -b claude/review-changes origin/main`, then `pnpm install`.
2. Verify each issue still reproduces before fixing it (the review ran against main at commit 81bae1e). Fix the root cause the recommendation names; where a recommendation is a sketch, use judgement and keep the change proportionate. Every ref must end up fixed, or explicitly deferred with a reason in the PR body.
3. Add or update tests for what you change: unit/data tests in vitest (`src/**/*.test.ts`), and update `e2e/smoke.spec.ts` where behaviour intentionally changes. Never delete or skip a test to get green.
4. Before every push run `pnpm check` (typecheck + lint + vitest + build) and `pnpm run build && PW_CHROMIUM_PATH=/opt/pw-browsers/chromium-1194/chrome-linux/chrome pnpm run test:e2e`. Look at the result in a real browser (Playwright screenshots of the states you changed, desktop and phone, dark and light) before calling it done.
5. Generated data files (`*.generated.json`, `public/feed.*`) come from their scripts — regenerate with the `pnpm run data:*` script rather than hand-editing; if the network blocks a source, make the script change, keep the committed file consistent, and say so in the PR.
6. Commit in logical steps. Push with `git push -u origin claude/review-changes`.
7. Open a pull request against `main` titled `Review batch 5: The 'what changed' engine`. Body: one section per move, a checklist of every issue ref (fixed / deferred + why), before/after screenshots where visual, and test notes. Then subscribe to the PR's activity and drive it to green: fix CI failures, address review comments, and when `main` moves (other batches merge) merge `main` into your branch and resolve conflicts carefully, keeping both sides' intent. Do not merge the PR yourself.
